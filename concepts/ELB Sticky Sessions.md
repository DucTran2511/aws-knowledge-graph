# ELB — Sticky Sessions

**Sticky Sessions** (also called **Session Affinity**) is a feature of [[Elastic Load Balancer (ELB)]] that ensures all requests from the **same client** are always routed to the **same target** behind the load balancer for a configurable duration.

By default, a load balancer distributes every single request across targets in a round-robin fashion. With stickiness enabled, the LB "pins" a client to a specific target using a **cookie**.

---

## Why Sticky Sessions Exist

Many applications store **session state** locally on the server:
- Shopping cart contents
- Login session / authentication tokens
- Form wizard progress
- In-memory caches specific to the user

If request #1 goes to Instance A (where the user logged in) but request #2 goes to Instance B, Instance B has no idea who the user is — the session is lost.

```
WITHOUT Stickiness:

Client ──► ALB ──► Instance A  (login, session created)
Client ──► ALB ──► Instance C  (session not found! ← user sees login page again)
Client ──► ALB ──► Instance B  (session not found! ← broken experience)


WITH Stickiness:

Client ──► ALB ──► Instance A  (login, session created)
Client ──► ALB ──► Instance A  (session found ✓)
Client ──► ALB ──► Instance A  (session found ✓) ... always Instance A
```

---

## Where Stickiness Works

| Load Balancer | Stickiness Type | Mechanism |
|---|---|---|
| **[[Application Load Balancer (ALB)\|ALB]]** | Cookie-based | HTTP cookie (3 types — see below) |
| **[[Network Load Balancer (NLB)\|NLB]]** | Source IP-based | Hashes source IP to pick a target (no cookie) |
| **CLB** | Cookie-based | Duration-based cookie (`AWSELB`) |
| **[[Gateway Load Balancer (GWLB)\|GWLB]]** | Flow-based | 5-tuple hash (src/dst IP, src/dst port, protocol) |

> [!NOTE]
> ALB and CLB use **cookies** (Layer 7). NLB uses **source IP** (Layer 4 — it can't read cookies because it doesn't parse HTTP). GWLB uses the network **flow** (Layer 3).

---

## ALB Cookie Types (The Exam Focus)

ALB supports **three** types of stickiness cookies. Understanding the differences is critical for the exam.

### 1. Duration-Based Cookie (LB-Generated)

| Property | Value |
|---|---|
| **Cookie name** | `AWSALB` |
| **Generated by** | The ALB itself |
| **Duration** | You configure it (1 second – 7 days) |
| **How it works** | ALB sets the cookie on the first response. On subsequent requests, ALB reads the cookie and routes to the same target. When the duration expires, the cookie is regenerated and the client may be routed to a different target. |

This is the **simplest** type — you just set a duration and ALB handles everything.

### 2. Application-Based Cookie (LB-Generated)

| Property | Value |
|---|---|
| **Cookie name** | `AWSALBAPP` |
| **Generated by** | The ALB itself |
| **Duration** | You configure it in the Target Group settings |
| **How it works** | Similar to duration-based, but the stickiness is specifically tied to the Target Group. Useful when you want application-level awareness of stickiness. |

### 3. Application-Based Cookie (Custom / App-Generated)

| Property | Value |
|---|---|
| **Cookie name** | **You choose** (e.g., `MY_APP_COOKIE`) |
| **Generated by** | **Your application** |
| **Duration** | Your application controls the expiration |
| **How it works** | Your application sets a custom cookie in the response. You then tell ALB the name of this cookie so it can use it for routing decisions. This gives your application full control over when stickiness starts and ends. |

**Use case:** Your app knows that a user's session has ended (logout, timeout) and can stop setting the cookie — the next request is free to go to any target.

### Reserved Cookie Names
Your application must **never** use these names for custom cookies:

| Reserved Name | Used By |
|---|---|
| `AWSALB` | ALB duration-based stickiness |
| `AWSALBAPP` | ALB application-based stickiness |
| `AWSALBTG` | ALB Target Group stickiness (internal) |

> [!WARNING]
> If your application accidentally sets a cookie named `AWSALB`, it will **conflict** with ALB's own stickiness cookie and cause unpredictable routing behavior.

---

## CLB Cookie

| Property | Value |
|---|---|
| **Cookie name** | `AWSELB` |
| **Generated by** | The CLB |
| **Duration** | You configure it |

CLB only supports duration-based stickiness. No application-based cookies.

---

## NLB Stickiness

NLB operates at Layer 4 and **cannot read HTTP cookies**. Instead, it uses **source IP affinity**:

- NLB hashes the **client's source IP address**.
- All connections from the same source IP are routed to the same target.
- This is configured at the **Target Group** level.
- No cookie is involved.

> [!WARNING]
> Source IP stickiness breaks if clients are behind a **NAT gateway** or **corporate proxy** — all clients appear to have the same source IP, so they all get routed to the same target, causing massive imbalance.

---

## How to Enable Stickiness

Stickiness is configured at the **Target Group** level (not on the ALB listener):

```
Target Group → Attributes → Stickiness

   ✅ Enable stickiness
   Type: [Load balancer generated cookie | Application-based cookie]
   Duration: [1 second – 7 days]
   App cookie name: [MY_APP_COOKIE]  ← only for custom app cookies
```

## The Problem with Stickiness — Load Imbalance

Stickiness trades **even distribution** for **session consistency**. This creates a fundamental tension:

```
Scenario: 3 instances behind an ALB

Instance A: 500 requests (a "power user" is stuck here)
Instance B:  50 requests
Instance C:  50 requests

→ Instance A is overloaded, B and C are underutilized!
```

### Why This Happens
- One user generates disproportionately more traffic (API automation, power user, bot).
- All users behind the same NAT/proxy appear as one "client" and get stuck to one target.
- Long stickiness durations mean the imbalance persists for hours or days.

### Mitigations
1. **Externalize session state** — Store sessions in [[ElastiCache]] (Redis) or [[DynamoDB]] instead of on the instance. Then you don't need stickiness at all.
2. **Shorten cookie duration** — Use the minimum duration that works (e.g., 5 minutes instead of 1 day).
3. **Use application-based cookies** — Let your app expire the cookie on logout/timeout so stickiness doesn't persist unnecessarily.
4. **Use Auto Scaling** — If one instance gets hot, [[EC2]] Auto Scaling adds capacity.

> [!IMPORTANT]
> **Best Practice:** The gold standard is to make your application **stateless** by externalizing sessions to [[ElastiCache]] or [[DynamoDB]]. This eliminates the need for sticky sessions entirely and allows the load balancer to distribute traffic perfectly evenly.

---

## Stickiness + Cross-Zone Load Balancing

Stickiness and [[Elastic Load Balancer (ELB)|Cross-Zone Load Balancing]] interact:

- **Without Cross-Zone:** Stickiness only applies to targets in the **same AZ** as the LB node the client connected to.
- **With Cross-Zone:** Stickiness applies across **all targets in all AZs** — the client can be sticky to a target in a different AZ.

For ALB, cross-zone is always on, so stickiness is always cross-AZ.
